# FlexNoC Packet Format & Protocol Specification

## 1. Scope & Status

This document defines the packet layout, field encoding, coordinate mapping, and ready/valid handshake semantics for **FlexNoC**. 
- **Protocol Version**: 1.0 (Baseline Frozen)
- **Packet Architecture**: Parameterized single-flit packet (with reserved forward-compatible packet-framing fields).
- **Physical Handshake**: Valid / Ready synchronous transfer.

---

## 2. Parameter Definitions

| Parameter | Default Value | Valid Range | Description |
| :--- | :--- | :--- | :--- |
| `FLIT_WIDTH` | 32 | $16 \dots 128$ | Total data bit-width carried per transfer link |
| `X_WIDTH` | 2 | $1 \dots 4$ | Bit-width for X coordinates (2 bits $\rightarrow$ up to $4\times N$) |
| `Y_WIDTH` | 2 | $1 \dots 4$ | Bit-width for Y coordinates (2 bits $\rightarrow$ up to $N\times 4$) |
| `PKT_ID_WIDTH`| 8 | $4 \dots 16$ | Packet sequence / diagnostic identifier width |
| `PAYLOAD_WIDTH`| 16 | Calculated | Available data payload width: `FLIT_WIDTH - 2*X_WIDTH - 2*Y_WIDTH - PKT_ID_WIDTH` |

> [!IMPORTANT]
> For default configuration (`FLIT_WIDTH=32`, `X_WIDTH=2`, `Y_WIDTH=2`, `PKT_ID_WIDTH=8`):
> `PAYLOAD_WIDTH = 32 - (2 + 2 + 2 + 2 + 8) = 16` bits.
> Width checks are enforced via SystemVerilog `initial begin static_assert ... end`. Silent bit truncation is strictly prohibited.

---

## 3. Bit Layout & Field Mapping

A 32-bit baseline flit is formatted with big-endian field ordering (MSB to LSB):

```
 31    30 29    28 27    26 25    24 23          16 15                         0
+--------+--------+--------+--------+--------------+-----------------------------+
| dest_x | dest_y | src_x  | src_y  |    pkt_id    |           payload           |
| (2 b)  | (2 b)  | (2 b)  | (2 b)  |    (8 b)     |           (16 b)            |
+--------+--------+--------+--------+--------------+-----------------------------+
```

### Detailed Field Descriptions

1. **`dest_x` (`[31:30]`)**: Destination router column coordinate.
   - Legal values in a $2\times2$ mesh: $0, 1$.
   - Legal values in a $4\times4$ mesh: $0, 1, 2, 3$.
2. **`dest_y` (`[29:28]`)**: Destination router row coordinate.
   - Legal values in a $2\times2$ mesh: $0, 1$.
   - Legal values in a $4\times4$ mesh: $0, 1, 2, 3$.
3. **`src_x` (`[27:26]`)**: Source router column coordinate of originating endpoint. Used for end-to-end scoreboarding, latency tracking, and response routing.
4. **`src_y` (`[25:24]`)**: Source router row coordinate of originating endpoint.
5. **`pkt_id` (`[23:16]`)**: Sequential transaction tag or packet sequence number, generated by the source endpoint to verify loss, duplication, and in-order delivery.
6. **`payload` (`[15:0]`)**: Uninterpreted user application data or command payload.

---

## 4. Coordinate System & Mesh Orientation

FlexNoC adopts a standard 2D Cartesian grid with origin at the **North-West (top-left)** corner:

- **X Coordinate**: Increases **Eastward (right)**: $0 \le X < \text{MESH\_WIDTH}$.
- **Y Coordinate**: Increases **Southward (down)**: $0 \le Y < \text{MESH\_HEIGHT}$.

```
      (X=0)            (X=1)
(Y=0) [Router (0,0)] <---> [Router (1,0)]
            ^                    ^
            |                    |
            v                    v
(Y=1) [Router (0,1)] <---> [Router (1,1)]
```

### Port Direction Encoding

Each router exposes five bidirectional logical ports, enumerated as follows:

| Port Identifier | Value | Direction / Description |
| :--- | :--- | :--- |
| `PORT_LOCAL` | `3'd0` | Local network interface (PE / Core / Traffic Generator) |
| `PORT_NORTH` | `3'd1` | Upward neighbor link ($Y - 1$) |
| `PORT_EAST`  | `3'd2` | Rightward neighbor link ($X + 1$) |
| `PORT_SOUTH` | `3'd3` | Downward neighbor link ($Y + 1$) |
| `PORT_WEST`  | `3'd4` | Leftward neighbor link ($X - 1$) |

---

## 5. Ready/Valid Flow Control Contract

Every point-to-point link consists of three signals:
- `data[FLIT_WIDTH-1:0]` (Sender $\rightarrow$ Receiver)
- `valid` (Sender $\rightarrow$ Receiver)
- `ready` (Receiver $\rightarrow$ Sender)

```
        Sender                                Receiver
   +--------------+      data[FLIT_WIDTH-1:0]     +--------------+
   |              |==============================>|              |
   |              |            valid              |              |
   |              |------------------------------>|              |
   |              |            ready              |              |
   |              |<------------------------------|              |
   +--------------+                               +--------------+
```

### Invariant Rules:

1. **Transfer Event**: A flit is atomically transferred from Sender to Receiver **if and only if** both `valid` and `ready` are sampled HIGH on the rising edge of `clk`:
   $$\text{Transfer} \iff \text{posedge(clk)} \land (\text{valid} == 1'b1) \land (\text{ready} == 1'b1)$$
2. **Stability Guarantee**:
   When `valid` is asserted HIGH by the Sender and `ready` is LOW (backpressure stall), the Sender **must hold `valid` HIGH and maintain `data` completely unchanged** in the next clock cycle:
   $$\text{valid}_t \land \neg \text{ready}_t \implies \text{valid}_{t+1} \land (\text{data}_{t+1} == \text{data}_t)$$
3. **No Speculative Acceptance**:
   The receiver must not latch data or modify internal state unless `valid && ready` is true.
4. **Decoupled Ready (No Combinational Loops)**:
   The router ingress port connects directly to an `input_fifo`. The link `ready` signal is driven by the FIFO capacity (`!fifo_full` or watermarked threshold). Ingress `ready` **never combinationally depends** on any egress `ready`. This mathematically prevents combinational cycles across the mesh.

---

## 6. Clock and Reset Semantics

- **Clock**: `clk`, single-domain synchronous network. Transfers occur on rising edges (`posedge clk`).
- **Reset**: `rst_n`, active-low asynchronous reset (or synchronous release).
- **Reset Contract**:
  - While `!rst_n`:
    - All link `valid` outputs are deasserted (`1'b0`).
    - All buffer occupancy pointers and counters reset to zero (`empty = 1`, `full = 0`).
    - All round-robin priority pointers initialize to `PORT_LOCAL` (`3'd0`).
  - No spurious transfers or indeterminate flits may emerge during or immediately exiting reset.

---

## 7. Invalid Destination & Boundary Policy

1. **Mesh Boundaries**:
   - For boundary routers (e.g., Row 0 has no North neighbor), nonexistent neighbor input links are tied off (`in_valid = 1'b0`, `in_data = '0`).
   - Boundary output ready signals are tied to `1'b0`.
2. **Out-of-Bounds Destination Handling**:
   - If a flit contains coordinates outside the configured mesh dimensions ($\text{dest\_x} \ge \text{MESH\_WIDTH}$ or $\text{dest\_y} \ge \text{MESH\_HEIGHT}$), route computation flags an `illegal_dest` error signal.
   - In standard mode, invalid flits are routed to `PORT_LOCAL` with an error diagnostic bit set or dropped with an error counter tick, preventing packets from getting trapped in infinite deflection loops or attempting to traverse nonexistent boundary links.

---

## 8. Multi-Flit Packet Roadmap (Forward Compatibility)

To support future virtual channels and multi-flit wormhole routing without redesigning interfaces:
- The flit layout reserves bit positions for a 2-bit flit type field: `FLIT_HEAD`, `FLIT_BODY`, `FLIT_TAIL`, `FLIT_SINGLE`.
- For Version 1 baseline, all packets are implicitly `FLIT_SINGLE`, ensuring full payload throughput and eliminating wormhole head-of-line blocking while establishing verified routing and flow control.
